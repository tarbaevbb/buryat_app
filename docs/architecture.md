# Архитектура приложения

## Общая картина

```
Telegram WebApp (или браузер)
        │
        ├── React 18 + Vite + Tailwind (HashRouter)
        │       │
        │       ├── данные курса (src/data)      — статика, вшита в бандл
        │       ├── состояние (src/store)        — zustand + persist → localStorage
        │       └── Telegram SDK (src/telegram)  — тема, кнопки, haptics, mock
        │
        └── Supabase (опционально)
                ├── Edge Function telegram-auth  — проверка initData → сессия
                ├── Postgres + RLS               — профили, прогресс, XP, ошибки
                └── RPC                          — fn_fetch_progress, fn_push_progress,
                                                   fn_award_lesson, fn_award_review,
                                                   fn_reset_progress, fn_leaderboard_week
```

Ключевой принцип: **приложение работает без сервера**. Если `VITE_SUPABASE_URL`
и `VITE_SUPABASE_ANON_KEY` не заданы, `supabase` равен `null`,
`isCloudEnabled === false`, и весь прогресс живёт в `localStorage`.
В профиле это отражается бейджем «Локально» / «Облако».

## Данные и упражнения

`src/data/vocab/unitN.ts` — плоские списки лексики с тегами:

```ts
{ id: 'ger', bxr: 'гэр', ru: 'дом', transcription: 'гэр', pos: 'noun',
  tags: ['reading', 'home'] }
```

`src/data/course.ts` описывает 5 разделов и 25 уроков **декларативно**:
у каждого урока указаны теги, из которых собирается пул слов, и список
предложений. Поэтому добавление лексики не требует правок в логике уроков.

`src/data/exercises.ts` генерирует задания из этого описания:

| Тип | Как строится |
|---|---|
| `select` (перевод) | слово урока + 3 дистрактора той же части речи |
| `select` (чтение) | транскрипция + 2–3 варианта от других слов |
| `build` | предложение урока, слова перемешаны + 2–3 слова-дистрактора |
| `match` | 5 пар слов урока (стабильная перестановка по сиду) |

Порядок заданий детерминирован: сид — `hash(id урока)`. Один и тот же урок
всегда даёт один и тот же набор, поэтому прогресс не «прыгает» между сессиями.

## Проверка ответов

`src/lib/normalize.ts`:

- `normalize` — регистр, пунктуация, пробелы;
- `looseKey` — дополнительно сводит ө→о, ү→у, һ/h→х, й→и;
- `isCorrect` — точное совпадение либо совпадение по `looseKey`.

Это прощает типичные опечатки (пользователь без бурятской раскладки пишет
«уhан» вместо «уһан») и не наказывает за почти верный ответ.

## Состояние

- `progressStore` — XP, гемы, сердца (с таймером восстановления), серия дней,
  результаты уроков, статистика по словам, XP по дням. Persist в localStorage.
- `sessionStore` — текущий урок: индекс задания, фаза (`answering` / `checked` /
  `done`), ошибки, статистика. Логика чистая, без React — поэтому легко тестируется.
- `settingsStore` — звук, вибрация, показ транскрипции.

Сводка по уроку (`sessionSummary`) считает XP так: 10 базовых + 5 за идеальное
прохождение (или 3 при точности ≥ 80 %) + 1 за каждые 2 задания с первой попытки.

## Геймификация

| Механика | Правило |
|---|---|
| Сердца | 5 штук, −1 за ошибку, +1 каждые 30 минут, восстановление за 50 💎 |
| Серия | +1 при занятии в новый день, сброс при пропуске > 1 дня |
| XP / уровень | 100 XP = 1 уровень |
| Идеальный урок | ≥ 95 % без единой ошибки → «золотая» звезда |
| Гемы | +1 за каждые ~5 XP |

Важное: при потере сердца таймер восстановления запускается только если запас
был **полным** — иначе повторные ошибки бесконечно сдвигали бы восстановление.

## Telegram-слой

`src/telegram/init.ts` — единственная точка входа:

- `tg()` возвращает настоящий `Telegram.WebApp` или `createMockWebApp()`;
- `initTelegram()` вызывает `ready()` и `expand()`;
- `lockSwipes()` / `unlockSwipes()` — блокировка свайпов и подтверждение
  закрытия. Включаются **только** на экране урока: иначе приложение нельзя
  свернуть нигде, что раздражает;
- `haptic()` безопасно дёргает `HapticFeedback` (метода может не быть);
- `initDataRaw()` — сырой `initData` для передачи на сервер.

`theme.ts` раскладывает `themeParams` в CSS-переменные (`--tg-bg`, `--tg-text`
и т. д.) и подписывается на `themeChanged`, `safeAreaChanged`, `viewportChanged`.
Tailwind-тема ссылается на эти переменные (`bg-tg-bg`, `text-tg-hint`),
поэтому смена темы Telegram перекрашивает интерфейс без перерисовки логики.

`hooks.ts` (`useMainButton`, `useBackButton`) синхронизирует нативные кнопки
Telegram с состоянием экрана. В браузере MainButton mock-режима невидима,
и на экране урока показывается обычная кнопка — поэтому UX одинаков везде.

## Отклик: звук и вибрация

Компоненты не вызывают `haptic()` напрямую — они вызывают `feedback('correct')`
и подобное (`src/lib/feedback.ts`). Решение «вибрировать / звучать» принимается
в одном месте по актуальным настройкам профиля. Раньше вызовы шли напрямую,
и переключатель «Вибрация» ни на что не влиял.

| Событие | Вибрация | Звук |
|---|---|---|
| `tap` | лёгкая | щелчок |
| `select` | смена выделения | — |
| `correct` | успех | две ноты вверх |
| `wrong` | ошибка | низкий сигнал |
| `complete` | успех | мажорный аккорд |
| `heartLost` | сильная | две ноты вниз |

Звуки синтезируются через Web Audio API (`src/lib/sound.ts`) — файлов mp3 нет,
загрузок тоже, бандл не растёт. Браузеры блокируют звук до первого касания,
поэтому `primeFeedback()` вызывается в обработчиках тапов: он «будит»
аудиоконтекст, и первый же сигнал звучит как надо.

В браузере `HapticFeedback` эмулируется через `navigator.vibrate`
(работает в Chrome на Android; в iOS Safari вибрации для веба нет).

## Устойчивость к ошибкам

`ErrorBoundary` (`src/components/ErrorBoundary.tsx`) оборачивает приложение.
Без него любое исключение в рендере давало пустой экран — а в Telegram нет
ни консоли, ни адресной строки, поэтому пользователь не понимал бы, что
случилось. Граница показывает объяснение, кнопку перезагрузки и текст ошибки
в свёрнутом блоке «Подробности» (для диагностики).

## Облако

### Что синхронизируется

В облако уходит весь прогресс, а не только XP: результаты уроков, XP по дням,
статистика слов, сердца и серия. Синхронизация идёт через две функции:

```
fn_push_progress(payload)  ← полный снимок состояния с устройства
fn_fetch_progress()        ← полный снимок состояния с сервера
```

### Правила слияния

Правила слияния вынесены в чистую функцию `mergeProgress`
(`src/lib/progress.ts`) и продублированы в `fn_push_progress`. Их
согласованность проверяется тестом `schemaParity.test.ts`.

| Поле | Правило |
|---|---|
| XP, гемы | максимум |
| Результаты уроков | по каждому уроку берётся лучший score / accuracy / xp |
| XP по дням | максимум за день (не сумма) |
| Статистика слов | максимум по errors / seen |
| Серия | побеждает сторона с более поздней датой занятия; при равных датах — больший счётчик |
| Сердца | сравниваются «эффективные» значения (с учётом восстановления); побеждает большее |

Ключевое свойство: **все операции идемпотентны**. Повторная отправка
одного и того же снимка ничего не меняет, поэтому XP невозможно накрутить
повторными запросами и невозможно потерять при обрыве связи.

Отдельная тонкость — сердца. Сырое число без учёта времени сравнивать нельзя:
3 сердца с меткой «2 часа назад» означают полный запас. Поэтому обе стороны
сначала «материализуют» пару (число + метка) к текущему моменту
(`materializeHearts` на клиенте, `fn_hearts_now` на сервере), и только потом
сравнивают.

### Сценарии

**Первый вход.** `bootstrapCloud()` обменивает `initData` на сессию, читает
облачный снимок, сливает с локальным, отправляет результат обратно, если
он оказался больше.

**Завершение урока.** Локально награда начисляется сразу (мгновенный отклик),
затем `fn_award_lesson` считает XP на сервере, а `flushProgress()` догружает
полный снимок.

**Завершение повторения.** Так же, через `fn_award_review`. Раньше повторение
не влияло на серию и XP — теперь начисляет.

**Работа без сети.** Всё пишется в localStorage. `flushProgress()` вызывается
при возврате в приложение (`visibilitychange`), при появлении сети (`online`)
и раз в минуту. Ничего не теряется: очередь — это само состояние, а
отправляется только то, что изменилось (по подписи состояния).

**Второе устройство.** Проходит тот же путь: читает полный снимок, значит
карта уроков, XP по дням и статистика слов подтягиваются, а не только XP.

**Сброс прогресса.** `fn_reset_progress` чистит сервер. Если сети не было,
флаг `resetPending` в localStorage заставит синхронизацию обнулить облако
при первой возможности — иначе старые XP вернулись бы при следующем входе.

### Безопасность

- XP считает только БД (`fn_award_lesson`, `fn_award_review`), клиент
  присылает лишь `lesson_id`, `score` и `accuracy`.
- `fn_push_progress` не принимает XP, гемы, серию и `dailyXp` из payload:
  они игнорируются. За уроки, пройденные офлайн, XP считается на сервере
  по серверной формуле, поэтому накрутить опыт с клиента нельзя.
- Права на таблицы у ролей приложения отозваны — клиент ходит только
  через RPC. Атаки и их проверки описаны ниже.
- `telegram-auth` проверяет HMAC-SHA256 по секрету
  `HMAC_SHA256(bot_token, "WebAppData")` и отвергает `auth_date` старше 24 часов.
- Токен бота живёт только в секретах Edge Function.
- RLS на всех таблицах: каждая строка доступна только владельцу.
- View `leaderboard_week` не открыт напрямую — только через RPC
  `fn_leaderboard_week`, который отдаёт топ-50.

### Смена Telegram-аккаунта на одном устройстве

Сессия Supabase лежит в `localStorage` и общая для всех аккаунтов Telegram
в домене: Desktop и Web делят хранилище, а `initData` при этом разный.

Без проверки второй пользователь видел бы имя, XP, серию и историю уроков
первого. Поэтому при старте `checkSessionOwner()` сверяет `tg_id` из сессии
с `tgUser().id`:

| Ситуация | Что делаем |
|---|---|
| `tg_id` совпали | работаем как обычно |
| разошлись или в сессии нет `tg_id` | `signOut()` + `clearLocal()`, затем вход заново |
| нет `tgUser().id` (браузер без Telegram) | доверяем сессии, как раньше |

Важная деталь: используется именно `clearLocal()`, а не `reset()`. Второй
ставит флаг `resetPending`, и при синхронизации обнулилось бы **чужое**
облако — то есть пострадал бы предыдущий владелец сессии.

### Миграция со старой версии

Ключ localStorage менялся с `buryat-progress-v1` на `buryat-progress-v2`.
`migrateLegacyProgress()` вызывается в `main.tsx` до монтирования приложения
и переносит прогресс, если в новом ключе ещё пусто. Внутри стора есть
и `persist.migrate` — он дозаполняет недостающие поля при обновлении версии.

### Проверка подписи Telegram

Логика вынесена в `supabase/functions/telegram-auth/initData.ts`, а не
оставлена внутри обработчика. Причина практическая: её можно тестировать
без поднятия Deno и без сетевых вызовов.

Алгоритм: `secret_key = HMAC_SHA256(bot_token, "WebAppData")`,
`hash = HMAC_SHA256(data_check_string, secret_key)`. Порядок аргументов
легко перепутать, и тогда проверка молча не сходится никогда — тесты
сверяют результат с независимой реализацией через `node:crypto`.

### Проверки в CI

| Job | Что делает |
|---|---|
| `lint` | ESLint: `react-hooks` (зависимости эффектов), `jsx-a11y` (доступность) |
| `test` | типы приложения + 172 теста |
| `build` | сборка + контроль размера бандла (лимиты в `scripts/bundle-budgets.json`) |
| `deno` | `deno lint`, `deno fmt --check`, `deno check` для Edge Function |
| `migrations` | миграции на чистом Postgres: применяются, идемпотентны, RLS и RPC работают |
| `ci-ok` | единый итоговый статус для branch protection |

Плюс отдельные workflow: `secrets.yml` (gitleaks и проверка, что в репозиторий
не попали токен бота или ключи Supabase), `codeql.yml` (статический анализ
безопасности), `deploy.yml` (Pages), `deploy-supabase.yml` (миграции и
функция в облако).

Здесь же лежат локальные аналоги: `npm run verify` повторяет
`lint → typecheck → test → build → size`, а `npm run check:migrations`
поднимает Postgres в Docker и проверяет миграции (нужен Docker).

## Известные ограничения

- **Нет аудирования**: в браузерах нет бурятского TTS, а предзаписанных mp3 нет.
  Тип задания `listen` зарезервирован в `types.ts` под будущее расширение.
- **Контент не вычитан носителем** — см. `content-review.md`.
- **Лидерборд** показывает всех пользователей недели; при масштабировании
  понадобится разбиение на лиги, как в Duolingo.
- **Слияние прогресса «прощающее»**: если на одном устройстве сердца
  потратили, а на другом запас полный, синхронизация вернёт полный запас.
  Это сознательный выбор в пользу игрока; при необходимости правило легко
  ужесточить, добавив метку времени последней потери.
- **Синхронизация по подписи состояния**: отправляется только изменившееся.
  Если два устройства занимаются одновременно, побеждает «большее» значение
  (см. правила слияния), а не последняя запись по времени.
